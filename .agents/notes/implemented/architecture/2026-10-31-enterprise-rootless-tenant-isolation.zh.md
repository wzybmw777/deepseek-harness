# Agent Note: 企业租户强制登录并使用 rootless 容器

Status: implemented

[English](2026-10-31-enterprise-rootless-tenant-isolation.md) | 中文

## 问题

企业控制台此前允许未登录访客进入共享访客工作区。匿名会话因此无法在数据边界上与真实成员区分，租户命令也会与控制面一起运行在宿主上。

## 决策

企业控制台不再提供访客凭据、访客租户、匿名工作区或未登录的自动租户创建。工作台启动、会话授权以及所有租户 HTTP 和 WebSocket 路由都要求已签名的企业成员会话。未分配团队、团队停用、跨团队 URL 和旧访客 Cookie 都会在租户启动前被拒绝。

每个团队拥有一个由非特权服务账号按需启动的 rootless Podman 容器。容器在启动前必须报告 `Rootless=true`，运行时启用 `--readonly`、`--cap-drop=ALL`、`no-new-privileges`、内存与 PID 上限、受限 `/tmp`、只读镜像和应用树，并且只有该团队的持久根可写。发布端口仅绑定宿主回环；`slirp4netns` 禁用宿主回环访问。控制面代理已认证请求，并确保内部 Harness Cookie 不进入浏览器。

团队成员有意共享团队的容器、工作区、凭据、会话历史和进程状态。隔离单位是团队，不是成员。

## 考虑过的替代方案

**保留共享访客工作区以降低试用门槛。** 拒绝，因为匿名用户会与其他所有访客共享持久状态和租户权限。

**以服务账号为每个团队运行宿主子进程。** 拒绝，因为它无法在文件系统、网络、能力或进程边界上隔离控制面。

**把 Podman 或 Docker 套接字挂载进租户。** 拒绝，因为控制容器运行时等同于控制宿主。

**为每个成员分配一个容器。** 暂缓，因为产品当前共享团队工作区和凭据；成员级保密需要不同的存储和协作模型。

**为每个租户使用微虚拟机。** 这会增加硬件虚拟化边界，但也带来更大的镜像、启动、运维和宿主容量投入，当前单机部署尚未接受这些成本。

## 后果

所有企业用户都必须先登录才能进入工作台，初始管理员必须配置账号。Rootless 容器共享宿主内核，因此内核、Podman、crun 和镜像更新仍是关键安全维护。绑定到非回环宿主地址的服务仍可通过用户态网络访问；它们必须绑定回环地址或单独配置防火墙，目的地白名单需要出口代理。当前部署有硬内存和 PID 上限，但没有每容器 CPU 配额。旧访客或探测数据目录不会自动删除，删除前需要明确的备份决定。
